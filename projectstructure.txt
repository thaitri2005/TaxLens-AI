# TaxLens AI 

**Working title:** **TaxLens AI**
**Project type:** Cloud-native regulatory intelligence and LLMOps platform
**Target users:** Accountants, auditors, tax consultants, accounting firms, and in-house tax professionals
**Primary cloud:** Microsoft Azure
**Primary portfolio objective:** Demonstrate end-to-end AI platform engineering rather than another PDF chatbot.

**Implementation rule:** This is a long-term blueprint, not a claim that every component is required on day one. The build should start as a modular monolith and add infrastructure only when a measurable workload or portfolio objective justifies it. Sections below label the intended **MVP**, **later release**, or **stretch** scope without removing the long-term architecture.

The project’s central idea remains:

> TaxLens continuously collects Vietnamese tax regulations, structures and versions them, detects relevant changes, and helps tax professionals understand what changed, why it matters, and where the conclusion came from.

This preserves the original vision of a hybrid structured–unstructured system using Blob Storage, PostgreSQL, pgvector, Airflow, FastAPI, a self-hosted multilingual embedding model, Hugging Face routed inference, LangGraph, LangChain adapters, MLflow, RAGAS-style evaluation, authentication, monitoring, and automated deployment. The practical path is to introduce these in phases rather than operate all of them in the first local environment.

# 1. Product Definition

## 1.1 The problem

Tax professionals currently have to:

1. Notice that a new legal document has been issued.
2. Find and download it.
3. determine whether it concerns their work or clients.
4. Read a potentially long document.
5. Identify amendments, replacements, or referenced regulations.
6. Compare it with the previous version.
7. Write a summary.
8. Explain the impact to colleagues or clients.
9. Continue monitoring later guidance and amendments.

The difficult part is not merely finding legislation. It is answering:

* What changed?
* When does it become effective?
* Which taxpayers or transactions are affected?
* Does it replace an older regulation?
* Which sections should I read?
* What action should I consider?
* How confident is the system?
* What source supports the answer?

## 1.2 The solution

TaxLens performs four broad jobs:

### Regulatory ingestion

It checks selected government sources, detects new or changed documents, downloads them, extracts text and metadata, and records the ingestion history.

### Regulatory knowledge management

It stores original files, normalized text, legal metadata, relationships, versions, chunks, embeddings, and processing status.

### Regulatory intelligence

It produces summaries, comparisons, timelines, topic classifications, affected-audience tags, and organization-specific impact analysis.

### User delivery

It provides dashboards, search, cited question answering, saved topics, alerts, document comparison, and periodic regulatory digests.

# 2. Deliberate Scope

## 2.1 Initial legal domain

Start with **Vietnamese tax regulation only**.

Do not begin with all Vietnamese law.

The first supported categories should be:

* Value-added tax
* Corporate income tax
* Personal income tax
* Tax administration
* Electronic invoices
* Import and export tax
* Customs-related tax obligations

This scope is already large enough to justify the architecture while keeping collection, labeling, evaluation, and demonstration manageable.

## 2.2 Initial document types

Support these first:

* Laws
* Decrees
* Circulars
* Resolutions
* Decisions
* Official tax guidance
* Consolidated legal documents, where available

## 2.3 Initial data-source policy

For the portfolio version:

* Use a curated seed corpus for reliability.
* Implement one or two real source connectors.
* Design the system so that more connectors can be added later.
* Do not make the live demo entirely dependent on fragile government websites.
* Preserve downloaded source files so the demo continues to work when a website changes.

## 2.4 Language

The source corpus is primarily Vietnamese.

The system should support:

* Vietnamese questions and answers
* English questions over Vietnamese legal sources
* Vietnamese citations regardless of answer language
* Optional bilingual summaries later

# 3. Core User Workflows

## 3.1 Regulatory monitoring

A tax professional opens the dashboard and sees:

* New documents
* Recently effective documents
* Upcoming effective dates
* Recently amended documents
* Documents relevant to saved tax topics
* Documents that failed processing
* Weekly regulatory summary

## 3.2 Document discovery

The user searches by:

* Document number
* Title
* Issuing agency
* Tax category
* Issue date
* Effective date
* Status
* Free-text keyword
* Semantic meaning

## 3.3 Cited question answering

Example:

> What changed recently in electronic invoice requirements?

TaxLens should:

1. Understand the user’s intent.
2. apply metadata filters.
3. Retrieve relevant chunks.
4. Rerank the results.
5. Generate an answer.
6. Attach document-level and article-level citations.
7. State uncertainty when evidence is insufficient.

## 3.4 Regulation comparison

Example:

> Compare the latest circular with the regulation it replaced.

The system should produce:

* Added provisions
* Removed provisions
* Modified thresholds
* Changed deadlines
* Changed affected entities
* New obligations
* Relaxed obligations
* Relevant source passages
* Effective-date transition notes

## 3.5 Impact analysis

Example:

> I advise small e-commerce companies. Does this regulation affect my clients?

The system should use:

* The regulation
* User profile or saved business context
* Tax topic
* Company characteristics
* Retrieved legal evidence

The response should separate:

* Confirmed legal requirements
* Likely implications
* Suggested review actions
* Uncertain or context-dependent points

It must avoid presenting AI output as formal legal advice.

## 3.6 Notifications

Users can subscribe to:

* A tax category
* A legal document
* An issuing authority
* Keywords
* A saved company profile
* Effective-date reminders

Possible notification channels:

* In-app notification
* Email
* Weekly digest
* Later: Microsoft Teams, Slack, or webhooks


## 5.4 Document OCR

Use only when native extraction is unusable. The local MVP does not use Azure
Document Intelligence or a hosted OCR API.

Processing logic:

```text
Is the PDF text-readable?
    │
    ├── Yes → native PDF extraction
    │
    └── No  → local Tesseract OCR (`vie+eng`)
```

This avoids paying for OCR on digitally generated PDFs.

## 5.5 Generative inference

Use Hugging Face Inference Providers for:

* Summarization
* Structured comparison
* Query interpretation
* Answer generation
* Impact-analysis drafting
* Evaluation assistance

Hugging Face routed inference is **not** the embedding provider. It is the
current configurable chat provider for cited Q&A and comparison summaries.

The development default is `Qwen/Qwen3-4B-Instruct-2507:cheapest`. This small multilingual instruct model is currently routable through Hugging Face, while `:cheapest` asks Hugging Face to select the lowest-priced available provider for that model. Keep the model ID, routing policy, timeout, output cap, and budget in environment settings rather than hard-coding them. A provider availability failure, budget exhaustion, or invalid structured output must produce an evidence-only/unsupported response, never an automatic upgrade to a costlier model.

## 5.5a Self-hosted embeddings

The default embedding model is `intfloat/multilingual-e5-small`, packaged into the FastAPI Docker image from a pinned Hugging Face revision. The model runs on CPU inside the API container and writes vectors to pgvector in PostgreSQL.

Use it through one internal embedding interface:

```text
embed_passages([chunk text]) → normalized vectors
embed_query(question)        → normalized vector
```

The implementation must:

* prepend `passage: ` to indexed chunks and `query: ` to search queries;
* configure a maximum input length of 512 tokens and log truncation;
* persist model ID, pinned revision, vector dimension, content hash, and embedding timestamp;
* cache vectors by chunk-content hash and model revision;
* load the model once per container process, not once per request;
* download model files during Docker image build, not at Container Apps startup.

This removes per-vector API charges and external embedding network calls. The
API image keeps dependencies and the baked model in cache-stable layers so
source edits do not reinstall the expensive stack. Start with the model in the
API image for the first cloud slice; split it into a dedicated embedding worker
only if measured API cold starts, memory use, or ingestion throughput justify
the additional service.

## 5.8 Runtime platform

There should be two deployment tiers.

### Realistic MVP deployment

Use:

* Azure Container Apps or App Service for FastAPI
* Azure Container Apps for workers
* Managed PostgreSQL
* Blob Storage
* Key Vault
* Azure Container Registry
* Static Web Apps or Container Apps for the frontend

This is more affordable and realistically maintainable.

### CV stretch deployment

Demonstrate AKS configuration through infrastructure code:

* FastAPI deployment
* Background worker deployment
* Airflow deployment
* Frontend deployment
* Ingress
* Autoscaling
* Health checks
* Secrets
* ConfigMaps
* Resource limits

You do not need to keep an expensive AKS cluster running continuously. The repository can still contain a valid AKS deployment path.

## 5.9 Cost and effectiveness guardrails

The Azure mapping is a target deployment blueprint, not a requirement to keep every service running during development. Use this order:

1. local Docker Compose with PostgreSQL/pgvector and a seed corpus;
2. one low-cost Azure development environment with API, Blob Storage, PostgreSQL, and secrets;
3. add workers, scheduling, monitoring, and managed identity as the corresponding workflow becomes real; keep OCR inside the application image;
4. keep AKS, high availability, and production resource groups as infrastructure-code demonstrations unless sustained usage justifies them.

Control spend and improve effectiveness by:

* extracting native PDF text before using the local Tesseract fallback;
* caching normalized text, metadata, embeddings, and evaluation results;
* embedding high-priority or recently changed documents first;
* pinning the Hugging Face model revision so an image rebuild cannot silently change vectors;
* measuring embedding throughput, CPU time, image size, and cold-start latency;
* recording requested model, routed provider when returned, token, latency, and estimated-cost data for every request;
* configuring Hugging Face billing limits and a low maximum output-token cap before enabling generative endpoints;
* setting a development budget and disabling nonessential resources outside demos;
* measuring citation correctness and answer usefulness before increasing model size or adding infrastructure.

Azure prices vary by region, agreement, and usage. Use the Azure Pricing Calculator immediately before provisioning rather than hard-coding a monthly estimate in this blueprint.

# 6. Application Components

## 6.1 Source Connector Layer

Each source connector should implement the same interface.

```python
class SourceConnector:
    def list_documents(self, since: datetime) -> list[SourceDocument]:
        ...

    def fetch_document(self, document: SourceDocument) -> bytes:
        ...

    def fetch_metadata(self, document: SourceDocument) -> dict:
        ...
```

Responsibilities:

* Discover source documents
* Extract source URLs
* Retrieve source metadata
* Download files
* Respect retry and rate limits
* Record crawl timestamps
* Return standardized objects

Each connector should be isolated because source websites will change independently.

Suggested folder:

```text
ingestion/connectors/
  base.py
  official_tax_portal.py
  ministry_of_finance.py
  seed_corpus.py
```

## 6.2 Change Detection Service

Do not rely only on titles or URLs.

Calculate:

* File checksum
* Normalized-text checksum
* Source-page checksum
* Last-modified information
* Document number
* Version identifiers

Possible outcomes:

```text
NEW_DOCUMENT
UNCHANGED
NEW_SOURCE_COPY
CONTENT_UPDATED
METADATA_UPDATED
PROCESSING_RETRY
```

Every ingestion should be idempotent. Running the same DAG twice must not create duplicate legal records.

## 6.3 Extraction Service

Extraction sequence:

```text
Download
   ↓
Validate MIME type
   ↓
Detect file format
   ↓
Attempt native text extraction
   ↓
Measure extraction quality
   ↓
OCR if quality is insufficient
   ↓
Normalize encoding and whitespace
   ↓
Preserve page boundaries
   ↓
Store normalized output
```

Extraction quality signals could include:

* Number of extracted characters
* Ratio of alphabetic characters
* Broken-character frequency
* Empty-page percentage
* Page count consistency

* Individuals

* Exporters
* Importers
* Employers

Initially, use a controlled taxonomy rather than unconstrained labels.

## 6.7 Chunking Service

Chunk legal documents according to legal structure, not arbitrary token windows.

Preferred hierarchy:

```text
Document
  └── Chapter
       └── Section
            └── Article
                 └── Clause
                      └── Point
```

Chunking priority:

1. Article-level chunks
2. Clause-level chunks for long articles
3. Token-based fallback only when structural parsing fails

Each chunk should retain:

```text
document_id
version_id
article_number
clause_number
section_heading
page_start
page_end
effective_date
tax_category
legal_status
text
token_count
```

This is critical for useful citations.

## 6.8 Embedding Service

The default implementation is a local `multilingual-e5-small` runtime in the FastAPI image, with pgvector storing its output. Keep a provider interface so a managed embedding service can be evaluated later, but do not add an external embedding API to the MVP.

### Eagerly embed

* Titles
* Abstracts
* Metadata summaries
* Frequently used documents
* New high-priority regulations
* Article headings

### Lazily embed

* Long document bodies
* Historical low-demand documents
* Attachments
* Rarely queried guidance
* Archived or superseded materials

Workflow:

```text
New document arrives
      ↓
Metadata and text stored
      ↓
Priority score calculated
      ↓
High priority?
  ├── Yes → Embed immediately
  └── No  → Mark EMBEDDING_PENDING
                    ↓
             Embed on demand
                    ↓
               Cache forever
```

For the initial corpus, fully embed every article-aware chunk after processing. Lazy embedding remains useful only for later historical imports and large attachments.

## 6.9 Retrieval Service

Use hybrid retrieval:

```text
Structured filters
        +
PostgreSQL full-text search
        +
pgvector semantic search from local E5 embeddings
        +
Reranking
```

Retrieval stages:

1. Query classification
2. Metadata extraction from question
3. Apply date, category, agency, and status filters
4. Keyword search
5. Vector search
6. Reciprocal-rank or weighted fusion
7. Reranking
8. Context assembly
9. Citation validation

Example:

> What VAT changes became effective in July 2026?

The system should infer:

```json
{
  "category": "VAT",
  "effective_date_from": "2026-07-01",
  "effective_date_to": "2026-07-31",
  "status": "effective"
}
```

Then it searches only the relevant legal subset.

## 6.10 LangGraph Workflow

Do not create an unrestricted “autonomous legal agent.” The pre-M6 upgrade
uses LangGraph as a controlled orchestration layer around the existing domain
functions.

Use a controlled workflow graph.

```text
START
  │
  ▼
Authenticate and Load User Context
  │
  ▼
Intent Classification
  │
  ├── Document Lookup
  ├── Regulatory Question
  ├── Change Summary
  ├── Document Comparison
  ├── Impact Analysis
  └── Unsupported Request
          │
          ▼
Query Planning
          │
          ▼
Structured Filters
          │
          ▼
Hybrid Retrieval
          │
          ▼
Evidence Sufficiency Check
          │
      ┌───┴────┐
      │        │
Enough     Insufficient
      │        │
      ▼        ▼
Analysis   Clarify or refuse conclusion
      │
      ▼
Citation Validation
      │
      ▼
Response Generation
      │
      ▼
Logging and Evaluation
      │
      ▼
END
```

The graph provides CV value because it demonstrates:

* Stateful LLM workflows
* Tool calling
* Routing
* Evidence checks
* Deterministic control
* Error handling
* Observability

LangChain is used only at the model and prompt integration boundary for
provider adapters, structured output, and callbacks. It does not own the
PostgreSQL/pgvector retrieval implementation. LlamaIndex is intentionally not
added because it overlaps with the existing retrieval and citation modules.

# 10. Airflow DAG Structure

Airflow is the required scheduler for daily discovery, continuous ingestion,
weekly digests, and evaluation. It is not required to make the first
search/Q&A demo work, but it is required before the product is considered
cloud-ready. Start with the same task functions behind CLI commands, then
place those functions in DAGs once the processing path is stable and
idempotent.

## 10.1 Daily discovery DAG

```text
tax_regulation_discovery_daily
```

Tasks:

```text
start
  ↓
load_connector_configuration
  ↓
discover_source_documents
  ↓
normalize_discovery_results
  ↓
compare_against_catalog
  ↓
branch_new_or_changed
  ├── no_changes → record_success
  └── changes
         ↓
      download_documents
         ↓
      calculate_checksums
         ↓
      persist_raw_files
         ↓
      create_processing_jobs
         ↓
      trigger_processing_dag
         ↓
      record_success
```

```text
tax_document_processing
```

```text
extract_native_text
```

The stack above is the long-term target. OCR is not planned as an Azure service:
Azure hosts the container image, while Tesseract and its language data run
inside the API/worker container. For the core MVP, the active stack is
FastAPI, Next.js, PostgreSQL with pgvector, workspace-backed raw storage,
native extraction plus local Tesseract OCR, baked-in E5 embeddings, the
configurable Hugging Face chat adapter, LangGraph, LangChain, Airflow, MLflow
evaluation hooks, Docker Compose, pytest, and Alembic. Redis, monitoring, and
managed Azure services remain downstream M6/operations work.

# 25. The Project’s Core Identity

The project should always be described in this order:

1. **Continuous regulatory ingestion**
2. **Structured legal data and versioning**
3. **Hybrid legal retrieval**
4. **Evidence-grounded AI analysis**
5. **Alerts and professional workflows**
6. **LLMOps evaluation**
7. **Azure deployment and operations**

Never lead with:

> “It is a chatbot for Vietnamese tax law.”

Lead with:

> **TaxLens AI is a cloud-native regulatory intelligence platform that continuously collects and versions Vietnamese tax regulations, detects changes, and delivers cited analysis to accountants and auditors.**

That is the established project structure we should treat as the master blueprint going forward.
